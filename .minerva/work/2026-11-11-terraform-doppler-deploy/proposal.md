# Proposal: terraform-doppler-deploy

**Date**: 2026-11-11
**Status**: Shipped (2026-11-11)

## Goal

Every merge to `main` deploys the Etsy MCP server to Cloudflare with no manual step. Terraform owns the Cloudflare resources the Worker binds to. The Worker's secrets come from Doppler, not from hand-run `wrangler secret put`. Everything in the owner's one-time setup that can be scripted (the Doppler project and generated secrets, the state bucket, the GitHub environment and the CI credential) is one command; what is left by hand is creating accounts and tokens, the Etsy callback, and connecting the apps.

## Why

v1 (PR #5) is merged but has never been deployed: `deploy.yml` skips itself because no `CLOUDFLARE_API_TOKEN` is set. Today the R2 bucket and its lifecycle rule are made by hand-typed `wrangler` commands, KV namespaces are auto-provisioned by an unrecorded first deploy, and the eight Worker secrets live only in a local `.dev.vars` and in whatever was last `wrangler secret put`. Nothing records what production should look like, and rotating a secret means remembering the right command. The owner asked for Terraform for infrastructure, Doppler for secrets, and auto-deploy on merge to `main`.

The Cloudflare account is greenfield for this server (checked 2026-11-11: no `etsy-shop-mcp` Worker, no KV namespaces, no `etsy-shop-uploads` bucket), so Terraform creates everything and nothing has to be imported.

## Approach

### Who owns what

- **Terraform (`infra/`)** owns the account-level resources: the `etsy-shop-uploads` R2 bucket, its lifecycle rules (delete objects under `uploads/` after 1 day, as the README's manual command did; and R2's default rule for new buckets, abort unfinished multipart uploads after 7 days, restated because `cloudflare_r2_bucket_lifecycle` sets the whole rule list), and the `OAUTH_KV` and `SHOP_KV` namespaces (titles `etsy-shop-mcp-oauth` and `etsy-shop-mcp-shop`). The bucket and both namespaces — the three resources that hold data — carry `lifecycle { prevent_destroy = true }`; the lifecycle rules are configuration and do not. Outputs: the KV namespace ids keyed by binding name.
- **Wrangler** keeps owning the Worker script, its Durable Objects and migrations, the cron trigger and plain vars, exactly as `wrangler.jsonc` declares them. Terraform never touches the script, so bundling and DO migrations stay with the tool built for them.
- **Doppler** (project `etsy-shop-mcp`, config `prd`) is the single source of truth for every secret: the eight Worker secrets in `wrangler.jsonc`'s `secrets.required`, plus `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` for the pipeline.
- **GitHub** holds exactly one credential: `DOPPLER_TOKEN`, a read-only Doppler service token for `etsy-shop-mcp/prd`, stored as a secret of a GitHub Environment named `production` whose deployment branch policy allows only `main`. An environment secret is invisible to workflows on other branches, which a repository secret is not (the convention from the owner's seekless repo). The environment's protection is committed as `.github/environments/production.json` (in the spirit of `.github/rulesets/main.json`) and applied by a TypeScript module the bootstrap calls (`npm run apply-environment` runs it alone), and a test pins the JSON to custom branch policies of exactly `main`.

### Terraform

- `infra/versions.tf`: `required_version = "~> 1.14.0"` (S3-backend `use_lockfile` is GA from 1.11; the pessimistic pin keeps local `terraform fmt` in step with CI); `cloudflare/cloudflare` pinned exactly (`5.28.1`); `.terraform.lock.hcl` committed with hashes for `linux_amd64` and `darwin_arm64`. Both workflows install Terraform `1.14.7` (the version used locally) with `terraform_wrapper: false`, because the action's default wrapper echoes commands into stdout and copies output into step outputs, which would corrupt the script's `-json` parsing and contradict "nothing passes through step outputs".
- State in an R2 bucket `etsy-shop-mcp-tfstate` through the `s3` backend: `region = "auto"`, `use_path_style`, `skip_credentials_validation`, `skip_metadata_api_check`, `skip_region_validation`, `skip_requesting_account_id`, `skip_s3_checksum`, `use_lockfile = true`. The endpoint comes from `AWS_ENDPOINT_URL_S3` at run time (it contains the account id). A comment records that R2's honouring of the lockfile's conditional write is unverified, and that the real serializer is the deploy workflow's `concurrency` group: CI is the only writer. What keeps it so is that no one holds a `DOPPLER_TOKEN` outside the `production` environment (bootstrap pipes it straight into `gh`); the deploy script's refusal to run unless `GITHUB_ACTIONS` is `true` and `GITHUB_WORKFLOW_REF` names `deploy.yml` on `refs/heads/main` is an accident guard, not enforcement, and the comment and `deploy.md` say so. State changes beyond plain applies — recovering lost state (R2 keeps no object versions), renames, removals — go only through committed `import {}`, `moved {}` and `removed {}` blocks applied by CI, never a local `terraform import`; KV titles are unique per account, so lost state fails loudly on create instead of silently making empty namespaces.
- S3 credentials are derived, not stored: Access Key ID = the Cloudflare API token's id, Secret Access Key = SHA-256 of the token value. The id comes from `GET /user/tokens/verify`, falling back to `GET /accounts/{account_id}/tokens/verify` for an account-owned token; if both fail the deploy stops with a message naming the token's required permissions. The README names those permissions exactly: Account: Workers Scripts Edit, Workers KV Storage Edit, Workers R2 Storage Edit, Account Settings Read; User: Memberships Read.
- The state bucket itself is created once by the bootstrap script (it must exist before `terraform init`), not by Terraform.
- `npm run check:infra` runs `terraform fmt -check -recursive infra`, `terraform -chdir=infra init -backend=false -lockfile=readonly -input=false` and `terraform -chdir=infra validate`. It joins the AGENTS.md gate chain, and `tests/gate-integrity.test.ts` pins the script's exact text so it cannot be quietly emptied.
- `.gitignore` and `.prettierignore` gain `infra/.terraform/`, `infra/tfplan` and `wrangler.deploy.json`.
- `.github/dependabot.yml` gains a `terraform` entry for `/infra`.

### Deploy pipeline

`.github/workflows/deploy.yml` is rewritten. Triggers: `workflow_run` of CI completed on `main` (as today), plus `workflow_dispatch` with boolean inputs `bootstrap` and `allow_destroy`. One job, `environment: production`, `concurrency: deploy` (no cancel), `permissions: { contents: read, checks: read }`. Dispatch inputs reach shell steps only through `env:`, never `${{ inputs.* }}` interpolated into `run:`. Two jobs, because a workflow-level concurrency group is joined before any job condition, which let a run that would never deploy cancel a pending deploy of the tip (found in review):

1. **`gate` job** (no environment, no concurrency group): for `workflow_run`, deploy only a CI run for a push that succeeded; for a dispatch, only if the latest `ci-pass` check-run from GitHub Actions (`app.id` 15368, the integration the ruleset binds) on the tip of `main` concluded `success` (via `gh api .../commits/<sha>/check-runs`). Either way, deploy only the commit that is still the tip of `main` (a stale dispatch warns). It outputs `deploy` and `sha` and sees only `github.token`.
2. **`deploy` job** (`needs: gate`, `if: needs.gate.outputs.deploy == 'true'`, `environment: production`, job-level `concurrency: deploy`, no cancel). Its first step re-checks the tip of `main` against the gated sha, because "Re-run failed jobs" reuses the gate's old outputs and would otherwise deploy a stale commit over a newer one (found in review); such a re-run can still displace a pending deploy of the tip before it stops, so it warns and the runbook says to dispatch instead. The same step skips with a `::warning::` naming the bootstrap step if `DOPPLER_TOKEN` is empty, so the repo stays green before setup; it sees only a boolean "is `DOPPLER_TOKEN` set", never the token.
3. Then: checkout at the gated sha (`persist-credentials: false`), setup-node, `npm ci` (no secrets in env; the `--secrets-file` behaviour is confirmed against the wrangler version `package.json` pins, `4.160.0`, during work), `hashicorp/setup-terraform` (`terraform_wrapper: false`), all pinned by full SHA. No Doppler CLI is installed in CI: the script calls Doppler's API itself.
4. **One step runs `node scripts/deploy.ts`** directly (not through npm, so no npm process sees the token) with only `DOPPLER_TOKEN` in its env, plus `--bootstrap` and/or `--allow-destroy` from the dispatch inputs. The script:
   - refuses to run unless `GITHUB_ACTIONS` is `true` and `GITHUB_WORKFLOW_REF` names `deploy.yml` on `refs/heads/main` (an accident guard; see Terraform), so its mask commands never reach a terminal. There is no local deploy path; if Actions is down, the deploy waits;
   - downloads the config with `GET https://api.doppler.com/v3/configs/config/secrets/download?format=json` using the service token as a bearer token (scoped to `etsy-shop-mcp/prd`, so no project/config arguments), and drops the `DOPPLER_*` metadata keys;
   - emits `::add-mask::` before anything else prints, for exactly: the values of `secrets.required` and `CLOUDFLARE_API_TOKEN`, each line of multi-line values, and the string leaves of JSON values (`MCP_CLIENTS`, `TOKEN_ENC_KEYS`), skipping values shorter than 8 characters and the placeholder `unset` (masking those only blanks ordinary log text, e.g. `TOKEN_ENC_KID=k1`); the derived S3 secret is masked the moment it is computed;
   - reads `secrets.required` from `wrangler.jsonc` (JSONC parsed with the `typescript` package already in devDependencies) and fails, naming the missing keys but never values, if Doppler lacks any of them, before any Terraform or Wrangler call;
   - runs `terraform init -input=false -lockfile=readonly`, then `terraform plan -input=false -out=tfplan`, then reads `terraform show -json tfplan` and **refuses to apply** if any resource change includes `delete` (which also covers replacements), unless `--allow-destroy` was given; then `terraform apply tfplan`. `prevent_destroy` only guards a resource whose block still exists; this guard catches a merged PR that deletes or renames a block. Terraform's child env is an explicit allowlist: `PATH`, `HOME`, `CI`, `TF_IN_AUTOMATION`, `TF_INPUT=0`, `CLOUDFLARE_API_TOKEN`, `TF_VAR_account_id`, the derived `AWS_*` credentials and `AWS_ENDPOINT_URL_S3` — so no Worker secret and no `DOPPLER_TOKEN`;
   - reads `terraform output -json`, writes `wrangler.deploy.json` (gitignored and prettier-ignored, repo root so relative paths still resolve): `wrangler.jsonc` with each KV binding's `id` filled from the outputs, failing if any binding has no id. It prints the KV ids (not secret) so the runbook can use them;
   - writes exactly the `secrets.required` keys to a mode-0600 JSON file under the OS temp dir (`RUNNER_TEMP` in CI), runs `wrangler deploy --config wrangler.deploy.json --secrets-file <file>` (plus `--var ALLOWLIST_BOOTSTRAP:true` when bootstrapping) with an allowlisted child env (`PATH`, `HOME`, `CI`, `WRANGLER_SEND_METRICS=false`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`; no Worker secret, no `DOPPLER_TOKEN`), and deletes the file in a `finally`. Values are written as the strings Doppler holds; `MCP_CLIENTS` and `TOKEN_ENC_KEYS` are never re-serialized. Wrangler documents that process env overrides secrets-file values (for dotenv files); the JSON path does not expand env, so the scrubbed env is defence in depth, and a test pins it;
   - secrets never pass through `$GITHUB_ENV`, step outputs, command-line arguments or Terraform state.

The old `npm run deploy` (a raw `wrangler deploy`) is removed, since it would deploy uncommitted code to production without the Terraform KV ids or the Doppler secrets.

### Scripts are TypeScript

The deploy and bootstrap scripts are `.ts` modules under `scripts/`, run by Node 24's built-in type stripping (`node scripts/deploy.ts`). Node's type stripping does no module resolution, so relative imports end in `.ts`, which TypeScript accepts only with `allowImportingTsExtensions`; and Node rejects non-erasable syntax (parameter properties, enums), which `erasableSyntaxOnly` catches at typecheck. Neither flag can go in `tsconfig.node.json` (`tests/gate-integrity.test.ts` pins its options to exactly `lib` and `types`) or in the base `tsconfig.json` (`src/vault/token-vault.ts` uses a parameter property). So the scripts get their own `tsconfig.scripts.json`: it extends `tsconfig.json`, adds `types: ["node"]`, `allowImportingTsExtensions` and `erasableSyntaxOnly`, and includes `scripts/**/*.ts` **and the script tests under `tests/scripts/**`**. `tsconfig.node.json` adds `exclude: ["tests/scripts/**"]` (its pinned `compilerOptions` stay exactly `lib`/`types`), because a test that imports a script pulls the script's `.ts`-suffixed imports into whichever program typechecks the test (reproduced: TS5097 under `tsconfig.node.json`). `npm run typecheck` runs all three programs. `eslint.config.ts` adds `./tsconfig.scripts.json` to `parserOptions.project` and to the import-x resolver's `project` list — a lint-config extension, not a carve-out. `tests/gate-integrity.test.ts` gains pins that the new file extends the base and overrides no strict flag, that `typecheck` runs it, and that the coverage `include` contains `scripts/**/*.ts`; the rule-level lint pin also samples a `scripts/*.ts` file against the same rule list the tests use (`REQUIRED_ERROR_RULES` minus `agentic/one-export-per-file`, which applies only to `src/`). knip gains entry `scripts/*.ts`, `ignoreBinaries: ["terraform"]` (a system binary, not an npm package), (the entry points only, so unused exports inside modules are still reported) and project `scripts/**/*.ts`. The existing `.mjs` scripts keep their `no-console`/`disableTypeChecked` carve-outs, which deliberately do not extend to `.ts` (`deploy.md` says so).

They get the full type-aware lint rule set and the 300-line limit, so logic is split across small modules. They write output with `process.stdout.write`/`process.stderr.write` through one small output module, so no `no-console` carve-out is needed. Tests in `tests/` import their functions and inject a command runner and fetch, so failure paths are tested without real `terraform`/`wrangler`/`gh`/`doppler`. `scripts/**/*.ts` joins the coverage `include` under the same 90%/80% floors (a tightening). Probed during the propose gates: with `scripts/**/*.ts` in the coverage `include`, node-project tests produce per-file coverage for the scripts, and `scripts/check-coverage-floor.mjs` already floors every file in the summary; only its "src/" message and the `vitest.config.ts` comment change. Entry files contain no branch — each is one line, `await runCli(import.meta, main)` — and the small `runCli(meta, main)` helper holds the `meta.main` check and sets `process.exitCode`, unit-tested both ways; a test imports each entry in-process (inert, since `meta.main` is false under vitest). A `main()` guarded by an `if` in the entry file would measure 66.66% lines / 50% branches and fail the per-file floor. A spawn smoke test runs each entry point under plain `node` with an explicit env (no `GITHUB_ACTIONS`, no `DOPPLER_TOKEN`), as `tests/check-scripts.test.ts` does for the existing scripts, so a module that only works under vitest fails the gate.

### Owner bootstrap

`npm run bootstrap` (`scripts/bootstrap.ts`), run once locally by the owner after `doppler login` and `gh auth login`, idempotent and safe to re-run, in this order:

1. creates the Doppler project `etsy-shop-mcp` if missing;
2. collects `CLOUDFLARE_API_TOKEN` (hidden prompt) and `CLOUDFLARE_ACCOUNT_ID` (visible) if missing in `prd`, and verifies the token (user endpoint, then account endpoint);
3. checks prerequisites with that token and stops with instructions if missing: the account itself (`GET /accounts/{id}`, since a user-owned token verifies for any account id), R2 enabled on the account (needs a payment method; free tier covers this use) and a workers.dev subdomain registered (`GET /accounts/{id}/workers/subdomain`). Only after these checks pass are newly typed Cloudflare values stored in Doppler, so a typo is asked for again on the next run; a stored value that fails names `doppler secrets set` (found in review);
4. in `prd`, generates any missing `TOKEN_ENC_KEYS`/`TOKEN_ENC_KID`, `UPLOAD_SIGNING_KEY` and `MCP_CLIENTS` (Claude and ChatGPT entries with the redirect URIs the README lists, fresh 32-byte secrets), sets `ALLOWED_ETSY_USER_ID`/`ALLOWED_ETSY_SHOP_ID` to `unset` if missing, and prompts with hidden input for `ETSY_KEYSTRING` and `ETSY_SHARED_SECRET` when missing. Values go to `doppler secrets set` on stdin, never argv. It never prints a secret and never overwrites an existing one;
5. creates the `etsy-shop-mcp-tfstate` bucket if missing;
6. **always** applies `.github/environments/production.json` through the environment module — PUT the environment with `custom_branch_policies: true`, list its deployment-branch policies, add `main` if missing and delete any other, all through the injected `gh` runner so tests see every call — because GitHub auto-creates `production` without protection the first time a deploy run names it, which will happen as soon as this merges. It then reads both back and refuses to continue unless the policy list is exactly `main`;
7. if the environment has no `DOPPLER_TOKEN` (or `--rotate-doppler-token` is given), creates a read-only Doppler service token for `prd` and pipes it straight into `gh secret set DOPPLER_TOKEN --env production` on stdin; the token is never printed or put in argv.

Local development keeps `.dev.vars` from `.dev.vars.example`; the Doppler `dev` config is not used.

### CI gate

`ci.yml` gains a `terraform` job that runs `npm run check:infra` with the pinned Terraform (`terraform_wrapper: false`), and `tests/ci-structure.test.ts`'s expected-command table gains `terraform: ["npm run check:infra"]`. `check:infra` is text-pinned rather than failure-tested, because the `test` job has no Terraform; the PR says so. It joins `ci-pass`'s needs. `tests/ci-structure.test.ts` and `tests/gate-integrity.test.ts` are **extended, not loosened** (the PR says so): they pin the new job, that `ci.yml` never declares `environment: production`, the environment JSON (custom branch policies, exactly `main`), and `deploy.yml`'s shape — environment `production`; every action SHA-pinned; the only secret referenced is `secrets.DOPPLER_TOKEN`, and only in the gate step (presence check) and the deploy step; `github.token` only in the gate step; the dispatch path's `ci-pass` check; `checks: read`; `terraform_wrapper: false` and Terraform `1.14.7` in both workflows; dispatch inputs only via `env:`; no Worker secret named in the workflow.

### Alternatives considered

- **B — Terraform deploys the Worker too** (`cloudflare_worker` / `cloudflare_worker_version` with the built bundle). Rejected: Wrangler's bundling and Durable Object migrations would have to be re-expressed in HCL, and Worker secrets would land in Terraform state.
- **C — Terraform for the R2 bucket only**, KV left to Wrangler's auto-provisioning, Doppler set up by hand. Rejected: less infrastructure under code, two tools creating resources, and more manual setup, for no gain beyond a smaller diff.
- **Terraform managing Doppler and GitHub** through their providers. Rejected: CI's own credential would be managed by the state it unlocks, and secret values would sit in state.
- **Committing KV ids to `wrangler.jsonc`** instead of a generated deploy config. Rejected: the ids exist only after the first apply, which runs in CI, so the first deploy could not succeed without a manual commit in between.
- **`doppler run -- wrangler deploy`** with secrets injected as env. Rejected: `doppler run` does not mask values in logs, and every child process (including `npm`) would see every secret.
- **Doppler's GitHub OIDC identities** (no stored `DOPPLER_TOKEN`). Rejected for now: a paid-plan feature; the environment-scoped read-only token is the free equivalent.
- **Doppler's Cloudflare Workers sync integration.** Rejected: it would push secrets on its own schedule, out of step with deploys, and the first deploy needs every `secrets.required` value at once; one writer (the pipeline) keeps secrets and code versions together.
- **Doppler CLI in CI** (`dopplerhq/cli-action`). Rejected: the action pins its own SHA but not the CLI version it downloads, which then holds the token; one authenticated `fetch` is smaller and testable.
- **A local break-glass deploy.** Rejected: it would be a second, unserialized Terraform writer deploying an unvetted working tree, and its mask commands would print secrets to the terminal.
- **Plan on PRs.** Rejected: it would need a state-reading credential reachable from any in-repo branch; the delete guard covers the dangerous case instead.

## Open Questions

- **Boundary:** this unit is complete when its PR merges with every criterion met. The owner's bootstrap, the bootstrap dispatch and the first live deploy are outside its success criteria; a failure there is handled with `minerva:debug` and a fix PR, not by reopening this unit.

- Does R2 honour the S3 backend's `use_lockfile` conditional write? Unverified; the workflow's concurrency group is the real serializer either way. Record what the first apply shows. If R2 rejects the conditional PUT (rather than ignoring it) and `init`/`plan` fail, the fallback is to remove `use_lockfile` and rely on `concurrency: deploy`.
- After this merges, the owner runs the bootstrap and the bootstrap dispatch; this unit cannot verify a live deploy itself. The first real run is the check on the derived S3 credentials and the token's permissions.
